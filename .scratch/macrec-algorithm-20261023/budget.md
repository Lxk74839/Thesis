## 3 推理与输出参数

两主方法同类角色采用相同 effort 和输出额度；不强制实际 token 数相同。以下是请求额度的完整档，半档为各值的一半。

| 请求类型 | 完整档 max_output_tokens | 要求 |
| --- | ---: | --- |
| 需求解析 | 2,048 | 必要条件/一般偏好/未知及来源 |
| Manager Thought | 2,048 | 有限的决策说明，不要求泄露模型内部推理 |
| Manager Action | 4,096 | 工具动作或 D 完整排列/可核验修订 |
| User / Item Analyst | 8,192 | 偏好依据或全部 D 的紧凑匹配矩阵；源引用表共享，避免逐格复制标题 |
| 生命周期 Searcher | 4,096 | 查询/观察摘要、四态/引用/缺口，不生成材料 |
| Reflector | 4,096 | 定位问题与有来源修订建议 |

reasoning effort 的待验证集合为 `low,medium`，额度档为半档/完整档；它们是候选参数，不是关于 4Router 已支持这些设置的承诺。32 次核对使用准备执行的真实业务 Schema、实际 M 与较长输入，检查完成状态、完整候选、引用有效性、可见输出/usage、截断或格式失败。不会发送通用 ping、计价或新模型探针。

初始优先采用完整档/medium 作为性能对照配置；若业务检查显示其不能完整输出，则只可选择已通过的配置并记录依据。两档都通过时，不以“省 token”作为选择理由；按来源正确性、候选完整性和业务核验情况确定。两主方法使用同一个选定配置。若没有配置通过，停止并提交具体不适配证据，不在正式对照中静默降档或重复调试渠道。

输出额度包含何种 usage、渠道是否如实执行 effort 及请求上限，须按本轮实际响应记录；reasoning_tokens 若属于 output_tokens 子集不重复相加。参数缺省不等于关闭推理。辅助 compact S/M 保留原 1400 和省略 effort 的旧协议以便解释历史定义，明确单列，不能据此当作主对照的等预算消融。

按完整档、上述冷上限估算，N=16 的**请求输出额度之和至多 33,547,392 token**（主/消融 176 槽×180,224，特征 16×88,064，辅助 112×1,400，参数核对按 32×8,192 保守计）。这不是实际生成量、已验证硬限制或收费量。输入若每次约 3k—8k token，则粗略为 20.8M—55.6M；这仅为待业务核对的场景估计，不能当精确 token 计数。

沿用既有发送器能力；新入口设置请求体上限 128KiB、响应体 256KiB，解析产物 64KiB。额度不足、JSON 不全或超限均如实失败，不截掉不利候选，也不自动增额。若实际 M/矩阵形状无法在已通过配置中完整表达，先报告规格/预算问题，再确认调整；不能将只评分部分 D 的结果称完整 I1。
